6장. Pull Request (PR)

Pull Request (PR)는 "내 브렌치 작업을 기준 브렌치(main)에 합쳐도 되는지 검토 요청"하는 단계입니다.

5장에서 본 Merge/Pull 흐름 위에, 팀 검토 절차를 올린 형태가 PR이라고 생각하면 이해가 쉽습니다.

보통 흐름은 이렇습니다.

  1. 로컬 브렌치 작업을 리모트에 Push한다.
  2. PR을 열고 변경 내용을 설명한다.
  3. 리뷰를 받고 수정이 필요하면 같은 브렌치에 추가 커밋한다.
  4. 승인되면 main에 머지한다.

핵심은 "PR은 합치기 전에 한 번 더 확인하는 안전 장치"라는 점입니다. 작업 품질, 실수, 빠진 파일을 여기서 많이 잡아냅니다.

이 장 그래프 사용 팁

  • 그래프는 단계 슬라이드입니다. 상단의 ← / → / Play로 흐름을 넘겨 보세요.
  • 이 장은 흐름 이해에 집중하도록 히스토리 창을 숨겼습니다.

그림 6-1. Push → PR → 리뷰 반영 → Merge → Fetch → Pull

단계 버튼으로 PR 과정을 순서대로 재생할 수 있습니다. origin/main, origin/feature/login-ui는 내 local의 리모트 기준점이며, 마지막 단계에서 Fetch와 Pull 차이를 확인할 수 있습니다.

PR 머지 후 정리 루틴(추천)

아래 그래프(그림 6-2)는 PR 머지 직후 정리 루틴을 단계로 보여줍니다. 버튼으로 넘기면서 브렌치가 어떻게 정리되는지 확인해 보세요.

그림 6-2. 머지 후 브렌치 정리 루틴(삭제 → checkout main → Pull → 새 브렌치)

리모트 작업 브렌치를 지우고, main으로 돌아와 Pull로 최신화를 맞춘 뒤, 다음 작업 브렌치를 새로 만드는 흐름입니다.

  1. 리모트에서 머지된 작업 브렌치를 삭제한다.
  2. main으로 체크아웃한다.
  3. Pull로 main을 최신 상태로 맞춘다.
  4. 로컬 작업 브렌치를 삭제한다.
  5. 다음 작업은 새 브렌치로 시작한다.

왜 이렇게 하는가

  • 끝난 브렌치를 치워서 브렌치 목록이 깔끔해집니다.
  • 다음 작업을 항상 최신 main에서 시작해 불필요한 충돌을 줄일 수 있습니다.
  • 작업 단위가 분리되어 PR 리뷰 범위가 명확해집니다.
  • 잘못된 기준점에서 이어 작업하는 실수를 줄일 수 있습니다.
