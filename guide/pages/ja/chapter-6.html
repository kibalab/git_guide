第6章. Pull Request (PR)

Pull Request (PR) は、 「自分のブランチ作業を基準ブランチ（main）に取り込んでよいかレビューを依頼する段階」です。

第5章で見た Merge / Pull の流れの上に、チームのレビュー手順を載せたものが PR だと考えると理解しやすくなります。

ふつうの流れは次のとおりです。

  1. ローカルブランチの作業をリモートへ Push する。
  2. PR を開いて変更内容を説明する。
  3. レビューを受け、修正が必要なら同じブランチに追加 Commit する。
  4. 承認されたら main に Merge する。

要点は「PR は統合前にもう一度確認するための安全装置」だということです。 作業品質、うっかりミス、入れ忘れたファイルをここでかなり拾えます。

この章のグラフを見るコツ

  • グラフは段階スライドです。上部の ← / → / Play で流れを進めてください。
  • この章は流れの理解に集中できるよう、履歴ウィンドウを隠しています。

図 6-1. Push → PR → レビュー反映 → Merge → Fetch → Pull

段階ボタンで PR の流れを順番に再生できます。 origin/main と origin/feature/login-ui は 自分の local 側にあるリモート基準点で、最後の段階で Fetch と Pull の違いも確認できます。

PR Merge 後の整理ルーティン（推奨）

下のグラフ（図 6-2）は、PR Merge 直後の整理ルーティンを段階ごとに見せています。 ボタンで進めながら、ブランチがどう片づいていくか確認してみてください。

図 6-2. Merge 後のブランチ整理ルーティン（削除 → checkout main → Pull → 新しいブランチ）

リモートの作業ブランチを消し、main に戻って Pull で最新化したあと、 次の作業ブランチを新しく作る流れです。

  1. リモートで Merge 済みの作業ブランチを削除する。
  2. main に Checkout する。
  3. Pull で main を最新状態に合わせる。
  4. ローカル作業ブランチを削除する。
  5. 次の作業は新しいブランチで始める。

なぜこうするのか

  • 終わったブランチを片づけることで、ブランチ一覧が見やすくなります。
  • 次の作業を常に最新の main から始められるので、不要な衝突を減らせます。
  • 作業単位が分かれるため、PR レビューの範囲が明確になります。
  • 間違った基準点から作業を続けてしまうミスを減らせます。
